# Technical design: Platform agent orchestrator

**Status:** Proposed  
**Date:** September 16, 2026  
**Source:** [Product requirements](./PRD-agent-orchestrator.md)

This document defines the first-version architecture, storage model, runtime
contracts, API, and failure behavior. Implementation must preserve native
LangChain and LangGraph semantics instead of creating a second orchestration
framework.

## Scope and constraints

The first release includes the complete PRD scope. Development still proceeds
through vertical tracer bullets so every merged stage remains runnable.

The system has these fixed constraints:

- It runs locally for one unauthenticated user.
- FastAPI and the Vite development server bind to `127.0.0.1`.
- PostgreSQL with `pgvector` is the only required service.
- Python 3.12 and `uv` manage the backend.
- React, TypeScript, Vite, and Bun manage the frontend and root tasks.
- LangChain `create_agent()` builds every agent harness.
- LangGraph provides graph execution, checkpointing, interrupts, retry, and
  streaming.
- LiteLLM runs in process through `langchain-litellm`.
- SSE transports native LangGraph stream chunks.
- Agent, model, and tool revisions are immutable.

Background workers, Redis, user-defined code, expression languages,
reconnectable streams, and multi-user authorization are excluded.

## Dependency policy

All direct dependencies use exact versions in lockfiles. The first ticket must
run a compatibility spike and pin a mutually compatible set for:

- `langchain`
- `langgraph`
- `langgraph-checkpoint-postgres`
- `langchain-litellm`
- `litellm`
- `fastapi`
- `pydantic`
- `sqlalchemy`
- `psycopg`

The spike must prove `create_agent()`, structured output, middleware ordering,
PostgreSQL checkpoint setup, subgraph interrupts, `@task` replay, retry,
timeout, and `astream(..., subgraphs=True)`. If a PRD API has changed, adapt at
one of four seams only: model resolver, compiler, checkpointer setup, or stream
encoder.

## Process architecture

The local system has three processes:

1. PostgreSQL stores application rows, vectors, and LangGraph checkpoints.
2. FastAPI owns validation, compilation, execution, SSE, and projections.
3. Vite serves the React application during development.

FastAPI executes graphs inside request tasks. A disconnected SSE request
cancels its invocation after the latest durable checkpoint. There is no worker
or in-memory run coordinator. Resume on a new process reconstructs the exact
revision tree and invokes the graph against the same `thread_id`.

## Database design

Application tables use UUIDv7 primary keys generated by the backend,
`timestamptz` timestamps, foreign keys, and `jsonb` only for validated
configuration. LangGraph owns its checkpoint tables; Alembic must not modify
them.

### Stable identities and revisions

Stable identity tables point to current revisions but never contain executable
configuration.

`kind` is one of `http`, `mcp`, `retrieval`, or `code`. Database constraints
check these bounded values and positive revision numbers. Pydantic performs full
JSON Schema and per-kind validation.

### Dependency pinning

Each publish resolves the complete dependency tree. The immutable
`dependency_manifest` records all referenced revision IDs and implementation
versions in deterministic order.

```json
{
  "models": ["0199..."],
  "tools": ["0199..."],
  "agents": ["0199..."],
  "code_tools": [
    {"implementation_key": "clock.now", "implementation_version": "1"}
  ]
}
```

A relational table enforces retention and supports reverse lookup.

```text
agent_revision_dependencies
  owner_revision_id uuid references agent_revisions(id) on delete restrict
  dependency_kind text not null
  dependency_revision_id uuid not null
  primary key(owner_revision_id, dependency_kind, dependency_revision_id)
```

`dependency_revision_id` is polymorphic, so the publish transaction verifies it
and installs explicit delete guards. Revision deletion is omitted from the
first API. This avoids relying on a polymorphic foreign key for integrity.

Publishing performs one serializable transaction:

1. Lock the stable agent row.
2. Validate the draft and resolve active dependency revisions.
3. Reject cycles and unavailable dependencies.
4. Produce canonical JSON and its SHA-256 content hash.
5. Insert the revision and dependency rows.
6. Set `agents.active_revision_id`.
7. Commit all changes together.

Database triggers reject `UPDATE` and `DELETE` on revision rows. A future
retention migration can replace the delete trigger after defining safe archival.

### Credentials

Credentials are encrypted before persistence.

```text
credentials
  id uuid primary key
  name text not null unique
  kind text not null
  ciphertext bytea not null
  nonce bytea not null
  key_version integer not null
  last_four text not null
  is_enabled boolean not null default true
  created_at timestamptz not null
  updated_at timestamptz not null
```

The backend uses AES-256-GCM from `cryptography`. `APP_ENCRYPTION_KEY` contains a
base64-encoded 32-byte key. Additional authenticated data is
`credential:{id}:v{key_version}`. Plaintext exists only inside the credential
resolver and never enters logs, exceptions, checkpoints, streams, or response
models. The API supports create, replace, list metadata, and disable; it never
returns plaintext.

### Conversations, runs, messages, and interrupts

LangGraph checkpoints are authoritative. These tables are rebuildable read
projections except for conversation metadata and the run's revision binding.

```text
conversations

  agent_revision_id uuid not null references agent_revisions(id) on delete restrict
  title text not null default ''
  parent_conversation_id uuid null references conversations(id) on delete restrict
  upgrade_summary text null
  created_at timestamptz not null
  updated_at timestamptz not null

runs
  id uuid primary key
  agent_revision_id uuid not null references agent_revisions(id) on delete restrict
  conversation_id uuid null references conversations(id) on delete restrict
  thread_id uuid not null
  mode text not null
  status text not null
  result_name text null
  result jsonb null
  usage jsonb not null default '{}'
  sanitized_error jsonb null
  started_at timestamptz not null
  finished_at timestamptz null

messages
  id uuid primary key
  conversation_id uuid not null references conversations(id) on delete cascade
  run_id uuid not null references runs(id) on delete cascade
  langgraph_message_id text not null
  role text not null
  content jsonb not null
  sequence bigint not null
  created_at timestamptz not null
  unique(conversation_id, langgraph_message_id)

run_interrupts
  id uuid primary key
  run_id uuid not null references runs(id) on delete cascade
  interrupt_id text not null
  kind text not null
  payload jsonb not null
  status text not null

```

`mode` is `conversation` or `orchestration`. `status` is `running`,
`interrupted`, `completed`, `failed`, or `cancelled`. A conversation turn uses
`thread_id = conversation_id`; a one-off run uses `thread_id = run_id`.

Projection writes are idempotent. Unique native message and interrupt IDs stop
duplicate stream chunks from creating duplicate rows.

## Agent revision document

The revision stores one canonical document. Unknown fields are rejected.

```json
{
  "schema_version": 1,
  "system_prompt": "## Role\n...\n## Rules\n...",
  "input_schema": {"type": "object", "properties": {}},
  "output_schema": {"type": "object", "properties": {}},
  "context_policy": {
    "memory": false,
    "knowledge_top_k": 0,
    "upstream": ["research"]
  },
  "middleware_policy": {
    "summarization": {"enabled": true},
    "context_editing": {"enabled": true},
    "pii": {"enabled": false},
    "tool_approval": {"risky_only": true}
  },
  "recursion_limit": 25,
  "entry_node_id": "research",
  "nodes": [],
  "edges": [],
  "named_exits": ["success"]
}
```

`memory` must remain `false` in version one. `knowledge_top_k` is zero unless a
retrieval source is configured. Node IDs match `^[a-z][a-z0-9_]{0,63}$` and are
unique inside one document.

## Node contracts

Only `agent` and `tool` are persisted node kinds.

### Inline agent node

An inline agent owns its harness configuration inside the root revision.

```json
{
  "id": "research",
  "kind": "agent",
  "agent": {
    "mode": "inline",
    "model_revision_id": "0199...",
    "system_prompt": "## Role\nResearch the request.",
    "input_schema": {"type": "object"},
    "output_schema": {"type": "object"},
    "tool_revision_ids": ["0199..."],
    "agent_tool_revision_ids": [],
    "context_policy": {"upstream": []},
    "middleware_policy": {},
    "review_output": false
  },
  "retry": {"max_attempts": 3},
  "timeout": {"run_seconds": 120, "idle_seconds": 30}
}
```

### Referenced agent node

A referenced agent runs as a private-state subgraph. Mapping uses field paths,
not templates.

```json
{
  "id": "writer",
  "kind": "agent",
  "agent": {
    "mode": "ref",
    "agent_revision_id": "0199...",
    "input_mapping": {
      "brief": ["research", "brief"]
    }
  },
  "retry": {"max_attempts": 2},
  "timeout": {"run_seconds": 120, "idle_seconds": 30}
}
```

The compiler creates fresh subgraph state for each invocation and omits an
explicit subgraph checkpointer so the parent checkpointer can persist interrupts
without cross-invocation memory. Only the validated named result is copied to
`outputs.writer`.

### Deterministic tool node

A tool node invokes exactly one pinned tool revision.

```json
{
  "id": "send_email",
  "kind": "tool",
  "tool_revision_id": "0199...",
  "input_mapping": {
    "to": ["compose", "recipient"],
    "subject": ["compose", "subject"],
    "body": ["compose", "body"]
  },
  "retry": {"max_attempts": 1},
  "timeout": {"run_seconds": 30, "idle_seconds": 15}
}
```

A mutating tool must receive the generated `run_id:node_id:task_sequence`
idempotency key or use one attempt. Tool output must validate against its output
schema and be JSON-serializable before entering state.

## Edge contracts

Edges use an explicit `kind`. Routing isn't represented as a node.

### Direct and terminal edges

```json
{"kind": "direct", "source": "research", "target": "writer"}
```

```json
{
  "kind": "exit",
  "source": "writer",
  "result_name": "success"
}
```

### Semantic routing

The source path must resolve to an enum in the source node's output schema.
Every enum value must have a route or an explicit default.

```json
{
  "kind": "semantic",
  "source": ["triage", "route"],
  "routes": {
    "billing": "billing_agent",
    "technical": "support_agent"
  },
  "default": "unsupported"
}
```

### Mechanical routing

Mechanical routing supports one comparison. Allowed operators are `eq`, `ne`,
`lt`, `lte`, `gt`, `gte`, `in`, `not_in`, `is_null`, and `is_not_null` where
the JSON Schema types permit them.

```json
{
  "kind": "mechanical",
  "source": ["request", "status"],
  "operator": "eq",
  "value": "success",
  "then": "writer",
  "else": "failure"
}
```

### Join edge

A join names all required sources and one target. Sources must be distinct.

```json
{
  "kind": "join",
  "sources": ["research", "analysis"],
  "target": "writer",
  "join": "all"
}
```

The compiler emits `add_edge(["research", "analysis"], "writer")`. No `any` or
quorum mode exists.

## Runtime state

All root graphs use one internal state shape.

```python
class RuntimeState(TypedDict):
    messages: Annotated[list[AnyMessage], add_messages]
    outputs: Annotated[dict[str, JsonValue], merge_node_outputs]
    result_name: str | None
    run_id: str
    usage: Annotated[dict[str, Usage], merge_usage]
```

`merge_node_outputs` rejects duplicate writes for the same node in one
superstep. Each node returns only its own key. Control data not intended for the
model remains outside prompt assembly.

Sub-agent `ref` graphs use private state. Parent input mapping creates the
subgraph input, and the wrapper validates and copies only its final result.

## Compiler design

The compiler is synchronous in structure and async where dependency resolution
or graph invocation requires it. It has four public seams.

```python
class RevisionRepository(Protocol):
    async def load_tree(self, revision_id: UUID) -> RevisionTree: ...

class ModelResolver(Protocol):
    async def resolve(self, revision: ModelRevision) -> BaseChatModel: ...

class ToolResolver(Protocol):
    async def resolve(self, revision: ToolRevision) -> BaseTool: ...

class GraphCompiler(Protocol):
    async def compile(self, tree: RevisionTree) -> CompiledStateGraph: ...
```

Compilation follows a deterministic order:

1. Load the pinned revision tree in one repository operation.
2. Verify its stored manifest and deployment code-tool versions.
3. Resolve model and tool objects without exposing credentials.
4. Build sub-agent revisions bottom-up.
5. Build every agent harness with `create_agent()`.
6. Wrap deterministic tool calls in the generic `@task` adapter.
7. Add nodes, direct edges, joins, conditional edges, and exits.
8. Apply retry and timeout policies.
9. Compile the root with the shared `PostgresSaver`.
10. Cache the compiled graph by root revision ID inside the process.

The cache is bounded and disposable. It contains runtime objects, never secrets
in serialized form. A process restart recompiles from immutable rows.

## Middleware order

The compiler owns middleware order. User configuration only enables supported
capabilities and parameters.

The outer-to-inner order is:

1. Run and node context middleware.
2. Model call limit middleware.
3. Tool call limit middleware.
4. PII input middleware, when enabled.
5. Dynamic prompt and upstream context middleware.
6. Summarization middleware, when enabled.
7. Context editing middleware, when enabled.
8. Large tool-set selector middleware, when enabled.
9. Model retry middleware.
10. Human-in-the-loop tool approval middleware, when enabled.
11. Sanitizing tool error middleware.
12. Usage projection middleware.

The compatibility spike must verify actual nesting semantics. Tests assert
observable order rather than private middleware internals. Tool retry middleware
is prohibited because task and node retry own retry behavior.

## Prompt assembly

The static `system_prompt` and tool descriptions remain the stable prefix.
Dynamic middleware appends one delimited context block immediately before
conversation messages.

```text
<context source="upstream" untrusted="true">
...
</context>
```

Only node IDs listed in `context_policy.upstream` are included. Values are
serialized with size limits and an untrusted-data marker. Retrieved text is also
marked untrusted. Neither block can add system-level instructions.

Summarization starts at 70 percent of the known context window and retains the
latest 30 percent. A model revision without a known context window must define
an absolute token trigger. Publishing rejects an enabled summarizer with no
usable threshold.

## Tool adapters

### HTTP

The HTTP adapter supports explicit methods, URL templates limited to declared
path parameters, credential-backed headers, JSON requests, JSON responses,
timeouts, and an optional idempotency header. It validates request and response
schemas.

Before each request, it resolves DNS and rejects loopback, private, link-local,
multicast, unspecified, and metadata-service addresses unless the exact host is
in a local allowlist. Redirects are disabled by default; each enabled redirect
is validated again. URL credentials and arbitrary proxy environment variables
are ignored.

### MCP

The MCP adapter supports Streamable HTTP only. A revision pins the server URL,
remote tool name, schemas, and credential reference. The same network policy as
HTTP applies. `stdio` lifecycle management is deferred.

### Retrieval

The retrieval adapter embeds the query, performs bounded cosine search in one
knowledge base, and returns JSON-safe chunks. `top_k` has a low configured
maximum. Raw retrieved text is untrusted context.

### Code registry

Code tools are registered during process startup.

```python
registry.register(
    implementation_key="clock.now",
    implementation_version="1",
    factory=create_clock_tool,
)
```

Publish fails when an exact key and version aren't present. Source code is never
stored in PostgreSQL or accepted from the UI.

## Validation

Draft validation checks shape only and returns path-addressed diagnostics.
Publish validation additionally proves executability.

The publish validator performs these passes:

1. Parse the versioned document with strict Pydantic models.
2. Validate supported JSON Schema features.
3. Check IDs, references, reachability, and paths to an exit.
4. Detect graph cycles and require a conditional exit and recursion limit.
5. Detect transitive `ref` cycles.
6. Resolve and pin active dependency revisions.
7. Validate field mappings and compatible JSON Schema types.
8. Validate semantic enum routes and mechanical operators.
9. Validate joins, named exits, and root output compatibility.
10. Reject agent-as-tool dependencies containing transitive HITL.
11. Verify model credentials and code registry implementations.
12. Canonicalize and persist the immutable revision.

Diagnostics use this shape:

```json
{
  "code": "mapping.type_mismatch",
  "path": "/nodes/2/input_mapping/body",
  "message": "Source is an array but the tool requires a string.",
  "severity": "error"
}
```

Only the implemented JSON Schema subset is accepted. Version one supports
objects, arrays, scalar types, required fields, enums, nullable unions, and
bounded numeric or string constraints. `$ref`, recursive schemas, custom
formats, and executable schema extensions are rejected until explicitly added.

## Persistence and resume

A migration command runs `PostgresSaver.setup()` once during deployment; normal
application startup doesn't run checkpoint DDL. Every invocation supplies a
`thread_id`.

- Conversation turn: `thread_id` is the conversation ID.
- Orchestration run: `thread_id` is the run ID.

HITL resume loads the run, recompiles its pinned revision, verifies one pending
interrupt, and invokes `Command(resume=...)` with the same thread config. Retry
invokes the graph with `None`. It never copies state from projections.

A sub-agent node that needs interrupts inherits parent checkpointing by omitting
an explicit checkpointer. It starts with fresh private state per invocation.
Agent-as-tool receives fresh state and cannot contain transitive HITL.

## HITL contract

One endpoint handles tool approval and node output review. Request models are a
discriminated union by `action`.

Tool actions are:

```json
{"interrupt_id": "...", "action": "approve"}
```

```json
{"interrupt_id": "...", "action": "edit", "input": {}}
```

```json
{"interrupt_id": "...", "action": "reject", "reason": "Not allowed"}
```

Node review actions are:

```json
{"interrupt_id": "...", "action": "accept"}
```

```json
{"interrupt_id": "...", "action": "revise", "output": {}}
```

```json
{"interrupt_id": "...", "action": "abort", "reason": "Cancelled"}
```

Edited tool input and revised node output must pass their pinned schemas. A
transaction locks the projection row before resume. A resolved interrupt returns
`409 interrupt_already_resolved`; an unknown or nonpending interrupt returns
`404 interrupt_not_found`. Reject becomes a structured tool result. Abort marks
the run `cancelled`.

All endpoints use `/api/v1`. JSON errors share this shape:

```json
{
  "error": {
    "code": "agent_revision_invalid",
    "message": "The draft cannot be published.",

  }

```

### Identity and draft APIs

The editor uses these endpoints:

- `POST /api/v1/agents`
- `GET /api/v1/agents`
- `GET /api/v1/agents/{agent_id}`
- `PUT /api/v1/agents/{agent_id}/draft`
- `POST /api/v1/agents/{agent_id}/draft/validate`
- `POST /api/v1/agents/{agent_id}/publish`
- `GET /api/v1/agents/{agent_id}/revisions`
- `GET /api/v1/agent-revisions/{revision_id}`

Draft writes require `version`. A stale version returns `409 draft_conflict` and
the latest version. Publish returns the existing revision when the canonical
content hash is unchanged.

Models and tools use equivalent identity, revision, list, and detail endpoints.
Updating executable configuration creates a new revision; it never mutates an
old one.

Credential endpoints are:

- `POST /api/v1/credentials`
- `GET /api/v1/credentials`
- `PUT /api/v1/credentials/{credential_id}`
- `POST /api/v1/credentials/{credential_id}/disable`

### Conversation APIs

`POST /api/v1/conversations` creates a conversation pinned to the agent's active
revision. `POST /api/v1/conversations/{conversation_id}/messages` accepts:

```json
{"content": [{"type": "text", "text": "Hello"}]}
```

It returns SSE. `GET /api/v1/conversations/{conversation_id}` returns metadata
and projected history. `POST /api/v1/conversations/{id}/upgrade` creates a new
conversation pinned to the current active revision and stores a generated or
user-supplied summary; checkpoints aren't migrated.

### Run APIs

`POST /api/v1/agents/{agent_id}/runs` accepts the root input object and returns
SSE. The server resolves the active revision before creating the run.

- `GET /api/v1/runs/{run_id}` returns status, result, usage, and safe error.
- `GET /api/v1/runs/{run_id}/interrupts` returns pending projections.
- `POST /api/v1/runs/{run_id}/resume` accepts an HITL decision and returns SSE.
- `POST /api/v1/runs/{run_id}/retry` accepts no body and returns SSE.

Retry is valid only for `failed` or `cancelled`. Resume is valid only for
`interrupted`.

### Retrieval APIs

The minimum manual ingestion API is:

- `POST /api/v1/knowledge-bases`
- `GET /api/v1/knowledge-bases`
- `POST /api/v1/knowledge-bases/{id}/documents`
- `GET /api/v1/knowledge-bases/{id}/documents`
- `DELETE /api/v1/knowledge-bases/{id}/documents/{document_id}`

Document creation chunks and embeds synchronously with a bounded request size.
Large asynchronous ingestion is deferred.

## SSE protocol

Responses use `Content-Type: text/event-stream`, disable proxy buffering, and
send UTF-8 JSON. Each SSE event has one `event` and one `data` field.

The opening event is:

```text
event: open
data: {"run_id":"...","thread_id":"...","revision_id":"..."}
```

Native chunks are wrapped without reinterpretation:

```text
event: native
data: {"namespace":[],"mode":"messages","chunk":{}}
```

The encoder converts LangChain messages, message chunks, tool calls, interrupts,
datetimes, UUIDs, and Pydantic models to JSON-safe values. It preserves native
metadata including `langgraph_node` and subgraph namespaces.

The final event is:

```text
event: close
data: {"status":"completed","result_name":"success","output":{},"usage":{}}
```

A sanitized runtime failure emits `event: error` followed by `event: close`.
Disconnect cancellation may prevent delivery of either event; the persisted run
status remains authoritative. No event replay or `Last-Event-ID` support exists.

## Run lifecycle and projections

The request transaction creates the run as `running` before streaming begins.
A stream observer updates projections idempotently from native updates.

- A native interrupt upserts `run_interrupts` and sets `interrupted`.
- A terminal result writes named output and sets `completed`.
- A handled exception stores a safe class and sets `failed`.
- Client cancellation cancels the invocation and sets `cancelled`.
- Resume marks the chosen interrupt resolved only after LangGraph accepts the
  resume command.

Projection failure must not corrupt checkpoint execution. It is logged with IDs
only, and the run becomes `failed` if the API cannot provide a trustworthy user
result. A rebuild command derives messages and interrupts from checkpoints.

## Retry and timeout

Node retry uses native LangGraph retry policy with exponential backoff and
jitter for classified transient failures. Validation, permission, schema, and
business rejections aren't retried.

All tool calls go through one deterministic task wrapper. Task sequence is
based on the stable tool-call order. Nondeterministic work happens inside the
task. Mutating tools require an idempotency key or one attempt.

Node functions are async. Native timeout policy applies `run_seconds` and
`idle_seconds`. The compatibility spike must establish the exact supported API;
no thread-based sync timeout fallback is allowed.

## Failure matrix

| Failure | Retry | Run status | Client result |
| --- | --- | --- | --- |
| Invalid draft | No | No run | `422 draft_invalid` |
| Publish graph invalid | No | No run | `422 publish_invalid` |
| Missing pinned dependency | No | `failed` | `409 dependency_unavailable` |
| Disabled credential | No | `failed` | Sanitized credential error |
| Model rate limit | Node policy | Running or `failed` | Native stream, then safe error |
| Model authentication | No | `failed` | Sanitized provider error |
| Tool transient network error | Task/node policy | Running or `failed` | Safe tool error |
| Tool schema mismatch | No | `failed` | `tool_output_invalid` |
| Mutating tool without idempotency | No retry | `failed` | Safe tool error |
| Node timeout | Policy | `failed` after attempts | `node_timeout` |
| Recursion limit reached | No | `failed` | `recursion_limit` |
| HITL interrupt | No | `interrupted` | Native interrupt and close |
| Invalid HITL edit | No | Remains `interrupted` | `422 resume_invalid` |
| Duplicate HITL resume | No | Unchanged | `409 interrupt_already_resolved` |
| Client disconnect | Manual retry | `cancelled` | Connection closes |
| Process crash | Manual retry/resume | Last projection may be stale | State from checkpoint |
| Projection write failure | No hidden retry | `failed` | Safe projection error |
| Stream encoding failure | No | `failed` | Safe stream error if possible |
| SSRF policy rejection | No | `failed` | Safe network policy error |

Exceptions are classified into stable public codes. Logs may include exception
chains but must redact credentials, authorization headers, request bodies marked
sensitive, prompts, retrieved PII, and tool results.

## Security boundaries

Although the app is local, all external data remains untrusted.

- Both servers bind to `127.0.0.1` by default.
- The API sets explicit local development CORS origins.
- Credentials use AES-256-GCM and environment-held master keys.
- HTTP and MCP enforce DNS-aware SSRF controls on every request and redirect.
- Tool input and output pass pinned schemas.
- Prompt and retrieval blocks are marked untrusted and size limited.
- Errors pass through allowlisted public classes and messages.
- SSE and projections use the same redaction layer.
- Logs are structured and exclude payloads by default.
- Risky tools require HITL according to their pinned revision.

Disabling authentication is acceptable only while binding locally. Any remote
binding requires a separate threat model and authentication design.

## Frontend design

The frontend uses feature slices without a second domain model.

- TanStack Query owns server state and cache invalidation.
- React Flow renders agent and tool nodes plus persisted edge kinds.
- A schema-driven form edits the supported JSON Schema subset.
- An SSE client exposes `open`, native chunks, terminal status, and safe errors.
- The run viewer derives active nodes from native metadata.
- The editor autosaves drafts with optimistic `version` checks.
- Validation diagnostics map JSON Pointer paths to forms and canvas items.

No global state library is added initially. Local component state and TanStack
Query cover editor and run data. Add one only if cross-route client-only state
becomes demonstrably difficult.

## Observability

Structured JSON logs include `run_id`, `thread_id`, revision ID, node, subgraph
namespace, attempt number, duration, status, and safe error class. They exclude
message and tool payloads by default.

Usage aggregation reads model response metadata and merges per-node input,
output, and total tokens. Missing provider metadata is represented as unknown,
not zero. LangSmith integration is opt-in through environment configuration and
isn't required for acceptance tests.

## Testing strategy

Tests use the smallest boundary that proves behavior.

- Unit tests cover canonicalization, graph validation, mapping, redaction,
  encryption, SSRF classification, and stream encoding.
- Integration tests use PostgreSQL for revisions, projections, and checkpoints.
- Compiler tests use fake chat models and deterministic code tools.
- API tests consume actual SSE responses.
- Frontend tests cover editor diagnostics and stream rendering.
- Acceptance tests exercise each PRD scenario across process restarts.

No acceptance test requires a paid model or external network. One optional
manual smoke test uses a user-configured OpenAI-compatible provider.

## Acceptance gates

The release is complete only when these flows pass:

1. Publish and converse with a one-node agent across two turns.
2. Run parallel referenced agents, join them, route, and return a named result.
3. Interrupt a risky tool, restart FastAPI, approve it, and finish once.
4. Retry a transient failure without rerunning completed upstream nodes or tasks.
5. Resume an old run after publishing a new revision and retain old behavior.
6. Reject invalid drafts at publish while still allowing incomplete autosave.
7. Confirm credentials don't appear in logs, SSE, projections, or checkpoints.

## Deferred decisions

The following items remain intentionally deferred:

- Authentication and remote deployment.
- Background execution and reconnectable event replay.
- Mixed embedding dimensions and automated ingestion.
- Full JSON Schema support.
- Long-term memory and LangGraph Store.
- Evaluation dashboards and time-travel UI.
- Revision deletion and archival.
- MCP `stdio` servers.

Add them only when their corresponding product requirement is approved.
